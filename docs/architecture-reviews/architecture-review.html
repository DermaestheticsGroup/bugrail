1. Storage / sync / offline: one concept in a 979-line grab-bag

Strong

qa-app/js/utils.js 18-250 (Storage, KvMerge) · app.js 150-215, 287 · auth.js 226-320 · notifications.js 62 · workspace.js 97

Problem

Storage holds ~12 pieces of state (cache, revs, base, chain, seq, inflight, serverOnline, offlineBoot, unsynced key, onMerged, leaving). It calls Auth.role(), Auth.can() and Toast.show from inside the persistence code. Freshness policy (15s GET /api/kv, per-key refreshKey, SSE, isUserBusy) lives in App, a UI shell. localStorage is touched directly in 5 files with no seam.

Solution

One deep persistence-and-freshness module: optimistic lock, merge, unsynced queue, offline mode, live push, "don't redraw while typing". App and Auth stop knowing about revs, merges and EventSource.

Benefits

  • locality: sync bugs concentrate in one module instead of Storage + App + Auth
  • leverage: callers get get/save/subscribe; they stop learning rev and merge rules
  • storage.check.js needs a vm context with 10 stubs today; with a localStorage adapter and a fetch adapter (two real adapters: browser and in-memory test) the interface is the test surface
  • startLive, pullLive, refreshFromServer, isUserBusy become testable

2. Authorization implemented twice, different rules, server half untested

Strong

qa-app/js/auth.js 70-135, 177-186 · utils.js 448 · server/app.js 36-107, 160-175

Problem

Server trusts x-role, x-workspace, x-can-share headers sent by the client ("Not real authentication" per its own comment). Workspace visibility is re-derived in server/app.js and duplicates Auth.visibleFiles. The permission map lives in client settings, invisible to the server. Passwords are plaintext in settings.users. Security note: client-asserted roles mean a bypass is possible by design.

Solution

One "who may see or change what" module holding the rule set. The client/server seam becomes a real interface instead of a header convention; validateFilesWrite / validateBugsWrite / validateSettingsWrite become pure functions behind it.

Benefits

  • locality: a visibility rule changes in one place, not auth.js plus server/app.js
  • leverage: both tiers call the same rule module
  • server has "test": "node --test" and zero tests; pure rule functions are directly testable
  • contradiction risk between client and server rules disappears

3. Whole-array PUT contract leaks across the client/server seam

Worth exploring

server/app.js 14-30, 186-262 · utils.js 40-250 · app.js 72-76 · server/db.js

Problem

Server is a dumb KV store (6 ALLOWED_KEYS). Client PUTs whole qa_bugs / qa_testcases arrays; sendWithMerge builds JSON by string concatenation. Merge exists twice (KvMerge.merge client, 409 stale handshake server). Every ActivityLog.record rewrites the whole log plus a full broadcast. Form rules stay client-side while row rules are diff-based server-side.

Solution

Decide the persistence interface shape (record-level vs whole-array). Merge, diff validation and revision handling are all workarounds for the whole-array shape and would move behind one seam.

Benefits

  • locality: merge/rev/validation rules in one place
  • leverage: one contract, two adapters (HTTP, in-memory)
  • a contract test can run real client against real server; none exists today

4. File container duplicated across Test Case and Bug Report

Strong

qa-app/js/testcase.js 42-110 · bugreport.js 39-105 · utils.js 448, 637-735

Problem

files(), fileCount, create, rename, share, delete are near-identical in both modules. The only diffs are tc_file_* vs bug_file_* action names and labels. Both share App.state.files, so deleting a file is a cross-module concern. filedelete.check.js must load all of app.js to test it.

Solution

A File module owning create, rename, share, delete, visibility and code scope. Test Case and Bug Report become two kinds of content inside it.

Benefits

  • locality: a workspace-sharing bug is fixed once
  • leverage: one interface, 2 call sites now, more kinds later
  • file deletion tested through its own interface, not through App

5. Activity log: side effect scattered over ~40 call sites, three audit trails

Worth exploring

qa-app/js/activitylog.js 1-50 · bugreport.js (17 call sites) · testcase.js (13) · usermanagement.js (8) · auth.js · workspace.js

Problem

Every mutation does App.saveX(); ActivityLog.record(code, inline-built string). Bug status writes twice: bug.activity (feeds report.js, notifications) and the global ActivityLog. Auth.logAssignment is a third trail. actionGroupOf decodes codes via startsWith('tc_file_'), a string-prefix contract across 4 files.

Solution

Treat "a domain mutation happened" as one event. Bug history, global audit log and assignment notifications derive from it instead of 3 hand-written calls per site.

Benefits

  • locality: forgetting to log, or trails drifting, can only happen in one module
  • leverage: one event, N derived views
  • ActivityLog.selfTest only covers trim(); event-to-trail derivation becomes testable

7. DOM-coupled god modules and the App.state global

Speculative

qa-app/js/bugreport.js (1,366 lines) · testcase.js (930) · utils.js (979) · app.js 20-80

Problem

App.state is touched in ~140 places. Auth reads App.state.settings; App reads Auth 20 times: circular. Auth.loadSettingsRaw reads Storage directly to work around load ordering. Global search duplicates per-module visibility rules. Modules cannot be tested without DOM and a full App.

Solution

"The current workspace's data" becomes one thing modules receive instead of reaching into App.state and Auth. Large; do after 1, 2 and 4.

Benefits

  • locality: state ownership in one module
  • leverage: modules take data in, return results
  • Auth.can role matrix testable without App

Top recommendation: 4 first, then 1

Candidate 4 (File module) is the cheapest win: near-identical code in two modules, clear seam, low risk, immediate locality. Candidate 1 (Storage) has the highest leverage: three modules and three freshness mechanisms depend on it, and its current test needs 10 stubs. Candidate 2 matters most for security but needs a decision on real authentication first.
